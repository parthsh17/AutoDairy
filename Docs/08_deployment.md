# Deployment and Operations

## Local development

1. Install Node.js 20 or newer.
2. Run `npm ci`.
3. Copy `.env.example` to `.env.local` and provide the Supabase URL and anon key.
4. Run `npm run dev`.

Use `npm run lint`, `npm run typecheck`, `npm run test`, and `npm run build` before opening a pull request.

## Production deployment on Vercel

Create a Vercel project with the repository root as its root directory. The checked-in `vercel.json` uses `npm run build` and publishes `dist`. Configure these Vercel environment variables for Preview and Production:

- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_ANON_KEY`
- `VITE_MONITORING_ENDPOINT` (optional HTTPS ingestion endpoint)

Vite variables are public client configuration. Never expose Supabase service-role keys or database credentials in them.

Vercel Git integration can deploy previews for pull requests and production from the protected `main` branch. A manual CLI deployment should use `vercel pull`, `vercel build --prod`, and `vercel deploy --prebuilt --prod` with a secret `VERCEL_TOKEN`.

## GitHub Actions

`.github/workflows/ci.yml` runs dependency installation, lint, TypeScript, tests, and the production build for every push and pull request. `.github/workflows/dependency-review.yml` runs high-severity production dependency auditing and GitHub dependency review; outdated packages are reported without blocking unrelated pull requests.

The Husky pre-commit hook formats and lints staged files, then runs the TypeScript check. Hooks are local safeguards; GitHub Actions remains the required gate.

## Monitoring and logging

`src/lib/monitoring.ts` defines the provider interface and sends only normalized errors and route events to the optional monitoring endpoint. The React error boundary, browser errors, unhandled promise rejections, route transitions, and performance marks use this abstraction. `src/lib/logger.ts` emits structured entries and suppresses debug entries in production. Replace the HTTP adapter with a vendor SDK by implementing `MonitoringProvider`.

## Backup strategy

Use the in-app Backup & Restore screen to download a JSON backup before releases or database maintenance. Store backups outside the repository with restricted access and verify a restore in a non-production project periodically. Restoration validates the manifest before replacing local and remote records.

## Release checklist

- Confirm Supabase migrations and RLS policies are applied.
- Configure Preview and Production environment variables in Vercel.
- Run `npm run lint`, `npm run typecheck`, `npm run test`, and `npm run build`.
- Verify the manifest, service worker, install prompt, offline queue, and sync recovery on a deployed preview.
- Generate and securely store a backup.
- Promote the validated preview to production.
- Check application errors and sync status after deployment.

## Rollback strategy

Use Vercel's deployment history to promote the last known-good deployment, or run `vercel rollback` for the production project. Database migrations must be backward compatible because application rollback does not automatically roll back Supabase schema changes. Restore data only from a verified backup and follow the documented restore confirmation flow.

## Known limitations

- The browser print dialog is used for PDF export; a server-side PDF renderer is not included.
- Monitoring is provider-neutral and inactive until `VITE_MONITORING_ENDPOINT` or a replacement provider is configured.
- Vite reports a large JavaScript chunk warning during build because the chart and UI dependencies are bundled together; the build remains successful.
- iOS uses the standard web app install flow; platform-specific splash images are not generated by the application.
